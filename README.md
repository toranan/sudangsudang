# 오늘얼마?

소규모 사업장 사장님과 알바생을 위한 iOS 근태/급여 관리 앱입니다.
출퇴근 기록, 급여 계산, 직원 초대, 근무 승인, 개인 매장 관리, 그리고 매장별 공지/매뉴얼 기반 RAG 챗봇을 하나의 모바일 경험으로 묶었습니다.

## 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트 성격 | 개인 포트폴리오 iOS 앱 |
| 대상 사용자 | 소규모 매장 사장님, 알바생 |
| 핵심 문제 | 근태 기록, 급여 계산, 매장별 공지/매뉴얼 전달이 여러 도구에 흩어짐 |
| 해결 방식 | 역할 기반 홈, 매장별 근태/급여 관리, 공지/매뉴얼 RAG 챗봇 |
| 현재 구현 상태 | SwiftUI 앱, Supabase DB/RLS, Edge Function, 매장별 RAG 흐름 구현 |
| 검증 | iOS Simulator generic build 성공, `git diff --check` 통과 |

## 1. 문제 정의

소규모 매장의 운영 정보는 대체로 여러 도구에 흩어져 있습니다.

- 출퇴근 기록은 카카오톡, 메모, 종이 장부에 남습니다.
- 급여 계산은 엑셀이나 수기 계산에 의존합니다.
- 직원 초대와 퇴사 처리는 별도 절차 없이 구두로 처리됩니다.
- 마감 순서, 포스기 사용법, 공지사항은 단톡방 과거 메시지에 묻힙니다.
- 알바생은 매장마다 다른 규칙을 매번 사장님에게 물어봅니다.
- 사장님은 반복 질문, 급여 착오, 근무 승인 누락을 계속 관리해야 합니다.

이 앱의 목표는 사장님과 알바생이 같은 매장 데이터를 기준으로 일하고, 매장 운영에 필요한 정보가 앱 안에서 자연스럽게 흐르도록 만드는 것입니다.

## 2. 해결 방향

오늘얼마는 문제를 세 가지 흐름으로 나눠 해결합니다.

| 문제 | 해결 |
|---|---|
| 근무 기록이 흩어짐 | 앱 안에서 출근/퇴근 기록, 승인 상태, 월별 내역을 관리 |
| 급여 계산이 불명확함 | 시급, 야간수당, 주휴수당, 공제 방식, 월급일 기준으로 예상 급여 계산 |
| 매장 규칙 전달이 반복됨 | 사장님이 공지/매뉴얼을 등록하고, 알바생은 RAG 챗봇으로 질문 |

핵심은 단순한 근태 앱이 아니라, 매장별 운영 맥락을 저장하고 다시 사용할 수 있는 구조를 만드는 것입니다.

### 문제에서 해결까지

| 단계 | 사용자 문제 | 제품 해결 | 구현 근거 |
|---|---|---|---|
| 기록 | 출퇴근 내역이 흩어져 승인/정산 때 다시 확인해야 함 | 출근/퇴근 기록과 승인 상태를 앱 안에서 관리 | `work_logs`, 승인 상태 UI |
| 계산 | 예상 급여와 공제 금액을 알기 어려움 | 월별 예상 급여, 세후 예상 금액, 다음 급여일 표시 | 시급/수당/공제 계산 로직 |
| 전달 | 매장별 공지와 마감 매뉴얼이 단톡방에 묻힘 | 사장님이 공지/매뉴얼을 등록하고 알바생이 읽기 전용으로 확인 | `store_documents`, 역할별 화면 분리 |
| 질문 | 알바생이 같은 질문을 반복하고 사장님이 계속 답해야 함 | 매장 문서 기반 챗봇으로 질문 처리 | pgvector 검색 + Gemini 답변 |

## 3. 사용자 흐름

### 사장님

1. 카카오 로그인으로 앱에 진입합니다.
2. 매장을 생성하거나 기존 매장을 선택합니다.
3. 초대코드를 만들어 알바생을 초대합니다.
4. 근무 기록을 확인하고 승인합니다.
5. 월별 예상 급여와 현재 근무 중인 직원을 확인합니다.
6. 매장 관리에서 공지와 매뉴얼을 등록합니다.
7. 직원들이 자주 묻는 질문은 매뉴얼 챗봇이 대신 답변합니다.

### 알바생

1. 초대코드로 매장에 합류합니다.
2. 매장 드롭다운에서 현재 일하는 매장을 선택합니다.
3. 선택된 매장 기준으로 오늘 급여, 이번 달 예상 급여, 세후 예상 금액을 확인합니다.
4. 출근/퇴근을 기록합니다.
5. 공지와 매뉴얼을 읽습니다.
6. 모르는 내용은 매장 챗봇에 질문합니다.

## 4. 주요 기능

### 역할 기반 홈

- 사장님과 알바생의 홈 화면을 분리했습니다.
- 사장님은 매장 운영과 직원 관리 중심으로 봅니다.
- 알바생은 선택된 매장의 급여, 출퇴근, 공지/매뉴얼 중심으로 봅니다.
- 두 역할 모두 매장 드롭다운을 사용해 현재 보고 있는 매장을 명확히 합니다.

### 근태/급여

- 출근/퇴근 기록
- 승인 대기/승인 완료 상태
- 월별 근무 시간 집계
- 시급 기반 예상 급여
- 야간수당, 주휴수당, 3.3% 원천징수, 4대보험 공제 방식 반영
- 월급일 기준 다음 급여일 표시
- 개인 매장 모드에서 알바생이 자기 기록을 직접 관리

### 초대/계정 관리

- 사장님이 초대코드를 생성합니다.
- 알바생은 초대코드로 매장에 합류합니다.
- 퇴사 처리와 개인 매장 삭제를 분리했습니다.
- 계정 삭제 Edge Function을 통해 사용자 데이터 정리를 처리합니다.

### 매장 공지/매뉴얼

- 사장님은 공지와 매뉴얼을 등록, 수정, 삭제할 수 있습니다.
- 문서는 카드 탭 시 바로 수정되지 않고 상세 보기로 열립니다.
- 수정/삭제는 점 메뉴에서 명시적으로 선택합니다.
- 알바생은 읽기 전용으로 공지/매뉴얼을 볼 수 있습니다.

### 매장별 RAG 챗봇

- 사장님이 등록한 공지/매뉴얼을 임베딩합니다.
- 알바생 질문은 해당 매장의 문서만 검색합니다.
- 검색된 문서를 기반으로 답변을 생성합니다.
- 문서가 없는 경우 fallback 답변을 제공합니다.

## 5. RAG 기능 설계

### 문제

매장마다 마감 순서, 레시피, 포스기 사용법, 청소 기준이 다릅니다. 일반 챗봇은 그 매장의 실제 규칙을 모르기 때문에 정확한 답을 하기 어렵습니다.

### 해결

매장별 문서를 벡터화하고, 질문이 들어오면 해당 매장의 문서만 검색한 뒤 답변을 생성합니다.

```text
사장님 문서 등록
  -> store-rag Edge Function
  -> OpenAI text-embedding-3-small
  -> store_documents 저장
  -> pgvector 검색 대상이 됨

알바생 질문
  -> 질문 임베딩 생성
  -> store_id 기준 문서 검색
  -> 검색된 문서를 Gemini에 컨텍스트로 전달
  -> 답변과 참고 문서 반환
```

### 구현 포인트

- `store_documents.embedding`은 1536차원 벡터입니다.
- `match_store_documents` RPC에서 `store_id`를 필터링합니다.
- RLS 정책으로 사장님은 관리, 알바생은 소속 매장 문서 조회만 허용합니다.
- Edge Function은 `index`와 `ask` 액션을 분리합니다.
- 앱에서는 사장님용 관리 화면과 알바생용 읽기 화면을 분리했습니다.

### 정확도를 위한 제약

- 질문 검색은 항상 `store_id`를 함께 전달합니다.
- 알바생 화면은 문서 수정/삭제 기능을 갖지 않습니다.
- 문서가 없거나 검색 결과가 부족하면 근거 없는 답변을 만들기보다 안내/fallback 흐름으로 처리합니다.
- 앱 내부에서도 로컬 문서 검색을 보조로 사용해 네트워크 실패 시 사용자가 완전히 막히지 않게 했습니다.

## 6. UX 개선 과정

### 문서 화면

초기에는 문서를 누르면 바로 수정 화면으로 이동했습니다. 하지만 사용자는 내용을 확인하려는 의도로 누를 가능성이 높기 때문에, 기본 동작을 상세 보기로 바꿨습니다. 수정/삭제는 점 메뉴로 분리해 실수 가능성을 줄였습니다.

### 챗봇 화면

초기에는 안내 문구와 입력창이 일반 카드처럼 배치되어 채팅 화면처럼 보이지 않았습니다. 이후 일반 메신저 패턴으로 바꿨습니다.

- 메시지 영역은 스크롤
- 입력창은 하단
- 사용자/봇 말풍선 좌우 분리
- 답변 중에는 타이핑 버블 표시
- 빈 화면에는 앱 캐릭터와 짧은 설명만 표시

### 알바 홈

초기에는 매장별 급여 카드가 여러 개 나열되었습니다. 매장이 많아지면 현재 어떤 매장을 기준으로 보는지 혼란이 생길 수 있어, 사장님 화면과 동일하게 매장 드롭다운 중심 구조로 바꿨습니다.

### Before / After

| 개선 영역 | Before | After |
|---|---|---|
| 매장 선택 | 여러 매장 카드가 나열되어 현재 기준이 흐림 | 드롭다운으로 현재 매장을 명확히 선택 |
| 문서 탭 | 문서를 누르면 바로 수정 화면으로 이동 | 문서 탭은 상세 보기, 수정/삭제는 점 메뉴 |
| 사장님/알바생 권한 | 같은 흐름을 재사용하면 기능 노출 위험이 있음 | 사장님 관리 화면과 알바생 읽기 화면 분리 |
| 챗봇 UI | 카드형 안내와 입력창이 섞여 채팅처럼 보이지 않음 | 하단 입력창, 말풍선, 타이핑 상태를 갖춘 메신저 패턴 |

## 7. 기술적 의사결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 벡터 저장소 | Supabase pgvector | 기존 DB/RLS와 같은 권한 모델 안에서 MVP를 빠르게 구현하기 위해 |
| 문서 검색 범위 | `store_id` 필터 + RLS | 매장 간 문서가 섞이면 정확도와 신뢰가 깨지기 때문에 |
| AI 호출 위치 | Supabase Edge Function | API Key를 앱에 노출하지 않고, 인덱싱/질문 로직을 서버에서 통제하기 위해 |
| 화면 구조 | 사장님/알바생 화면 분리 | 권한이 다른 사용자가 같은 UI를 공유할 때 생기는 혼란을 줄이기 위해 |
| 문서 기본 액션 | 상세 보기 우선 | 사용자가 문서를 누르는 1차 의도는 수정이 아니라 확인이라고 판단했기 때문에 |

## 10. 데이터/권한 설계

모든 핵심 데이터는 매장 단위로 분리합니다.

- `stores`: 사장님이 소유하는 매장
- `workers`: 매장에 속한 알바생 연결 정보
- `work_logs`: 매장/알바생 기준 근무 기록
- `store_documents`: 매장별 공지/매뉴얼/RAG 문서

권한 원칙:

- 사장님은 본인이 소유한 매장 데이터만 관리합니다.
- 알바생은 본인이 소속된 매장 데이터만 조회합니다.
- 매장 문서는 `store_id` 기준으로 검색하고 RLS로 한 번 더 보호합니다.
- API Key와 Edge Function secret은 저장소에 올리지 않고 환경 변수로 관리합니다.

## 13. 로컬 실행 준비

1. Xcode에서 `오늘얼마?.xcodeproj`를 엽니다.
2. `Config/Secrets.xcconfig` 또는 로컬 환경에 Supabase/Kakao 설정을 넣습니다.
3. Supabase migration을 적용합니다.
4. Edge Function secret을 설정합니다.
5. iOS Simulator 또는 실제 기기에서 실행합니다.

```bash
supabase db push
supabase secrets set --env-file Config/.env
supabase functions deploy store-rag
```

추가로 `git diff --check`로 공백 오류를 확인했습니다.

## 15. 포트폴리오 포인트

- 단순 CRUD 앱이 아니라 사장님/알바생 양면 사용자 흐름을 설계했습니다.
- 실제 사업장 운영 문제인 공지 전달, 마감 매뉴얼, 급여 혼란을 제품 흐름으로 풀었습니다.
- RLS와 `store_id` 격리로 멀티테넌트 데이터 안전성을 고려했습니다.
- AI 기능을 독립 기능이 아니라 매장 운영 문맥 안에 자연스럽게 배치했습니다.
- SwiftUI 화면 구조를 반복 사용성과 사용자 혼란 최소화 관점에서 개선했습니다.
- 문서 상세 보기/수정 분리, 매장 드롭다운, 읽기 전용 알바 화면 등 권한과 UX를 함께 고려했습니다.

## 16. 앞으로의 개선 방향

- 알바생용 급여 상세 분해 UI

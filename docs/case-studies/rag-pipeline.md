# 매장별 RAG 파이프라인

## 문제

마감 순서, 포스기 사용법, 공지사항은 매장마다 다릅니다. 범용 모델에 바로 질문하면 실제 매장 규칙이 아닌 그럴듯한 답을 만들 수 있습니다.

## 설계

```text
문서 등록/수정
  -> store-rag index
  -> text-embedding-3-small (1536차원)
  -> store_documents + pgvector

질문
  -> 질문 임베딩
  -> match_store_documents(store_id, top 5)
  -> 유사도 0.2 이상 문서만 Gemini 컨텍스트로 전달
  -> 답변 + 참고 문서 메타데이터 반환
```

## 주요 결정

- API 키를 앱에 넣지 않고 Supabase Edge Function secret으로 관리합니다.
- `index`와 `ask` 액션을 분리해 문서 관리와 질의 흐름을 명시했습니다.
- 검색 RPC와 RLS가 모두 매장 범위를 제한합니다.
- 답변 temperature를 `0.2`로 낮추고 문서 밖 내용은 모른다고 답하도록 지시합니다.
- 관련 문서가 없으면 생성 모델을 호출하지 않고 빈 출처와 안내 문구를 반환합니다.
- 답변과 함께 문서 ID, 제목, 종류, 유사도를 반환합니다.

## 결과

사장님이 등록한 ‘마감 방법’ 매뉴얼을 알바생이 자연어로 질문하고, 답변과 참고 문서를 확인하는 end-to-end 흐름을 구현했습니다. 문서 관리 권한과 검색 범위를 기존 Supabase 인증 체계 안에서 재사용했습니다.

## 한계와 다음 실험

- 현재 문서 하나를 하나의 임베딩으로 저장해 긴 문서 검색 품질이 떨어질 수 있습니다.
- `0.2` 임계값은 경험적 초기값이며 평가 데이터로 조정하지 않았습니다.
- 검색 적중률, 근거 충실도, 답변 거부 정확도를 측정하는 질문 세트가 없습니다.
- 프롬프트가 마지막 줄에 참고 제목을 요청하고 API도 출처를 반환해 표시가 중복될 수 있습니다.

다음 단계는 문서 청킹, 평가 질문 세트, 출처 클릭 이동, 네트워크 실패 관측 지표를 추가하는 것입니다.

# ADR 0003: 화면 데이터 새로고침 일관성

- 상태: Accepted
- 날짜: 2026-07-15

## 배경

SwiftUI의 `.task`, `.onChange`, 앱 활성화 알림, 당겨서 새로고침이 같은 조회 함수를 동시에 호출할 수 있습니다. 기존 구현은 120초 캐시를 화면마다 직접 관리했으며 일부 화면은 로딩 중인 같은 키의 요청을 무조건 무시했습니다. 이 때문에 사용자 새로고침이 서버 조회를 보장하지 않거나, 이전 매장·월의 늦은 응답이 현재 화면을 덮을 수 있었습니다.

## 결정

조회 화면은 다음 규칙을 공통으로 사용합니다.

1. 최초 진입과 앱 활성화는 120초 TTL 안에서 캐시된 화면 상태를 재사용합니다.
2. 사용자가 당겨서 새로고침하면 TTL과 진행 중인 요청 여부에 상관없이 새 요청을 시작합니다.
3. 캐시 키는 조회 결과를 결정하는 매장 ID, 직원 ID, 연월을 모두 포함합니다.
4. 각 조회는 `LatestRequest` 토큰을 발급하고 최신 토큰의 응답만 상태에 반영합니다.
5. 응답 직전에 캡처한 매장·직원·연월 키가 현재 화면 선택과 같은지 다시 검증합니다.
6. 서버에서 다시 받은 선택지에 현재 ID가 없다면 첫 유효 항목으로 조정하거나 화면 상태를 비웁니다.

## 이유

요청 취소만으로는 네트워크 계층이 취소를 즉시 준수한다고 보장할 수 없습니다. 반대로 로딩 중 요청을 모두 직렬화하면 사용자 강제 새로고침이 기존 요청을 기다리거나 무시될 수 있습니다. 요청은 병행할 수 있게 두되 상태 반영 권한을 최신 요청으로 제한하면 네트워크 구현과 무관하게 화면 일관성을 보장할 수 있습니다.

## 적용 범위

- 사장님 승인, 통계, 직원 관리, 일정 관리
- 알바생 근무 달력과 급여 내역
- 사장님 홈의 매장 선택 유효성 검증

고정된 단일 리소스를 조회하는 상세 화면은 같은 매장·월 전환 문제가 없어 이번 변경에서 제외했습니다.

## 보안 보완

커스텀 Supabase 접근 토큰은 `UserDefaults`에서 Keychain으로 이전했습니다. 기존 설치의 평문 토큰은 최초 실행 시 Keychain으로 마이그레이션한 뒤 삭제합니다.

## 검증

- 이전 요청 토큰 거부 및 명시적 무효화 단위 테스트
- 서명 없는 iOS Debug 빌드
- 매장·월 키 변경 후 이전 응답이 상태를 갱신하지 않는 코드 경로 검증

## 결과와 한계

당겨서 새로고침은 서버 요청을 새로 시작하고, 늦게 도착한 이전 응답은 화면에 반영되지 않습니다. 이 정책은 앱 내부의 조회 일관성을 다루며, 다른 기기의 변경을 자동 푸시하는 실시간 동기화는 별도의 Supabase Realtime 구독이 필요합니다.
